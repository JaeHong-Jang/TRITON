# 실행 그래프 구현 계획

## 목표와 완료 기준

사람의 판결을 유지하면서 실제 에이전트 전이, 복구 가능한 실행, 서버 공개/판결 조건, 화면의 실행 상태를 연결한다. 계약: `docs/contracts/execution.md`. 설계: `docs/design-docs/execution-graph.md`.

## 작업 소유

1. runtime 담당: court 워크플로/루프/모델·app 작업 큐/실행 저장소·해당 테스트.
2. guards 담당: API·장부·공개 projection·집계·관련 API 테스트.
3. frontend 담당: 공용 타입/클라이언트·실행 화면·법정 상태·모의 서버·프론트 테스트.
4. leader: 설계/계약/진행 현황·사건 실행 view·통합 검증·리뷰 조정·브라우저 확인.

서로의 파일을 되돌리지 않는다. 공용 계약을 먼저 고정하고 작업 경계를 지킨다. 제품 동작 변경은 회귀 테스트부터 작성한다. 코드는 한 줄 역할 주석과 기존 계층을 따른다.

## 결정

- 기존 Python과 원자적 JSON 저장을 확장한다. 단일 프로세스 로컬 환경에서 필요한 최소 구조이며 신규 의존성이 없다.
- 재개는 완료된 동일 입력 모델 호출 캐시 재사용 + 순수 도메인 재실행이다. 외부 부작용의 임의 재생은 지원하지 않는다.
- 그래프 스냅샷 없는 옛 재판은 기록 재생으로 표시하고 실행 이력을 꾸며내지 않는다.
- 새 사용자 지시 ‘개발 시작해’에 따라 문서 작성에서 구현으로 진행한다.
