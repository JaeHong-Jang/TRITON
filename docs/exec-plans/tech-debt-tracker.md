# 기술 부채

| 항목 | 영향 | 해결 방향 |
|---|---|---|
| 서기 판별력 낮음 (정상 기사 오판, 2026-10-07 서기 v2.3에서도 정상 14건 중 14건 낚시 판정) | 잘못된 처리 경로 권고가 사람에게 영향을 줄 위험 | 프롬프트만으로는 개선되지 않음(findings #14). 약식 처리 끄기 결정, 다른 모델 교차 검토 |
| 상대 근거 인정(concession) 사용 0건 | 에이전트가 반대 입장을 판단할 수 있다는 설계가 실제로는 쓰이지 않음 | 인정 유도 프롬프트 실험, 2심 반박과 연결 |
| 1심 자기 수정 0건 | 1심에서는 고쳐 쓰기 단계가 거의 돌지 않음 | 2심처럼 상대 근거를 보는 단계 추가 검토 |
| 모의 서버(`src/api/mock`)와 백엔드 이중 구현 | 계약 바뀔 때 둘 다 고쳐야 함 | 계약 테스트로 모의 응답 형식 점검 |
| 천칭 규칙 이중 구현 (`lib/scale.ts`, `court/scale.py`) | 규칙 변경 시 불일치 위험 | 같은 사례를 양쪽 테스트에 공통 고정 |
| 서버 실행 시간 | 로컬 단일 GPU에서 2심 약 1분 | 결과 캐시(이미 저장), 시연은 미리 생성 |
| 실제 `data/`에 이전 검증 잔여물 | 대시보드·통계에 테스트 기록이 섞임 | 제품 책임자 승인 후 정리 (`docs/exec-plans/active/next-steps.md`) |
| 실행 저장소는 JSON + 프로세스 내 잠금 | 여러 서버 worker 사이의 원자성·동시 실행 보장 없음 | 현재 단일 worker 유지, 필요 시 트랜잭션 저장소로 전환 |
| 일반 법정의 사건별 첫인상 게이트 | 여러 사람이 같은 서버를 쓰면 앞선 사람 기록으로 공개됨 | 다중 사용자 제품 전환 시 인증·세션별 권한 설계 |
| 실험실 C의 권고 공개 시점 | 현재 권고가 판결 입력 영역에 표시되지만 API 시간 게이트는 없음 | 실험 프로토콜 확정 뒤 별도 준비/판결 단계 추가 |
| 실행 그래프 변경의 실제 A.X 검증 없음 | 합성 테스트는 모델 판별력·GPU 처리량을 증명하지 않음 | 데이터·Ollama 준비 후 같은 시나리오 재실행 |
| 프롬프트/온톨로지 버전 고정은 해시 검사 | 이전 버전 파일 없이 달라진 실행은 재개 불가 | 장기 재현 요구가 생기면 내용 스냅샷 로더로 확장 |
| 그래프의 대규모 브라우저 부하 미측정 | SVG는 수천 노드에서 렌더·이벤트 비용이 증가할 수 있음 | 실제 기록 규모를 측정한 뒤 가상화·Canvas 전환 검토, 현재 필터·접기·목록 제공 |
| 저장 기록은 현재 조회 기능 | 시간에 따른 노드/근거 변화 재현을 화면에서 재생하지 않음 | 이벤트 시퀀스별 상태 투영·타임라인 계약을 별도 설계 |
| 프론트 단일 JS 청크 약 501.65 kB | Vite 500 kB 경고, 초기 로딩 비용(gzip 약 154.59 kB) | 화면별 지연 로딩을 별도 성능 작업으로 검토 |
| 반박 반감이 인용 일치만으로 적용됨 | 실제 A.X 반박 14건 모두 대상 근거가 그 주장을 뒷받침하지 못함을 보이지 못했는데도 상대 근거 무게가 절반이 됨 (findings #13) | 제품 결정 필요: 판사가 반박을 인정할 때만 반감하거나, 반박을 무게와 분리해 표시 (api.md 천칭 규칙 5 변경) |
| 프롬프트 규칙 단독 효과 미분리 | 자기 인용 모순·제목 표현 오귀속이 줄지 않아 프롬프트 변경의 득실이 불분명 | 새 코드 + 이전 프롬프트로 같은 사건을 다시 생성해 비교 |
| 프론트 타입이 새 집계 필드 미반영 | `cost.failedCalls`, `byCategory[].screeningSample`, `kpis.samples`가 API에는 있으나 `src/api/types.ts`·화면에 없음 | UI 단계에서 types.ts와 표시 함께 반영 |
